# 第一部分 · 通用得分句式库（背这些句式，任何题都能套）

## 1. 质量属性场景六元组（填空题必考）

```
① 刺激源（Source）      = 谁/什么引发（用户、管理员、外部系统、网络、攻击者）
② 刺激（Stimulus）      = 发生了什么（请求到达、链路中断、攻击、故障）
③ 制品（Artifact）      = 影响系统的哪个部分（必须细化到模块/中间件，不能写"整个系统"）
④ 环境（Environment）   = 运行在什么模式下（正常 / 高峰 / 故障降级 —— 三选一！）
⑤ 响应（Response）      = 系统做什么（动作，不是指标）
⑥ 响应度量（Measure）   = 量化标准（必须带数字和单位：ms、%、TPS、条/秒）
```

⭐ **两个铁律**：
- **环境必须区分"正常 / 高峰 / 故障模式"**，不能写"正常运行"
- **响应度量只写本场景相关指标**，不要把题干里所有目标数字都堆上去

**满分示例（断网恢复场景）**：

| 元素 | 满分答案 |
|---|---|
| ① 刺激源 | 边缘节点（KubeEdge 主节点） |
| ② 刺激 | 与云端 Kafka/控制面失联，断网持续 5 分钟 |
| ③ 制品 | 边缘网关数据缓冲模块（SQLite）+ 上传链路 |
| ④ 环境 | **网络降级/故障模式**（主用电信链路中断，备线未及时切换） |
| ⑤ 响应 | 本地 SQLite 继续缓存数据；网络恢复后按时间戳去重续传，业务不感知 |
| ⑥ 响应度量 | **数据零丢失**（24 小时缓冲容量）、**续传完成 < 30 秒**、掉线率 ≤ 0.1% |

## 2. 四类点判定句式（10 分题）

### 敏感点
> "**【某决策】是敏感点，因为它直接决定了【某质量属性】目标的达成**——一旦该决策变化，【属性】将显著波动。"

### 权衡点
> "**【某决策】是权衡点，它同时影响【属性 A（+）】与【属性 B（−）】**，是典型的架构取舍。"

### 风险点
> "**【某决策】是风险点，存在【单点故障／未验证／容量未知】隐患**，可能导致【后果】。建议引入【缓解战术】将其转化为非风险点。"

### 非风险点
> "**【某决策】是非风险点，采用了【业界成熟方案】，已有充分生产验证**，无技术不确定性。"

⭐ **每条必须附"因为……"**，无理由每点扣 0.5 分。

## 3. 战术答题公式（8-9 分题）

**公式**：`【战术类别】 + 在本架构中的落地形式 + 量化效果`

✅ **满分**：
> "**①【事件驱动 / 异步】战术**：Kafka 解耦云边链路，Flink 实时消费，告警从'轮询数据库'改为'流式触发'，延迟由秒级降至 50ms 内。"

❌ **扣分**：
- "用了 Kafka" —— 只有落地，没有类别
- "用了异步战术" —— 只有类别，没有落地
- 缺少量化 —— 扣 1 分

## 4. 效用树格式（12 分题）

**必须三层**：`质量属性 → 子属性 → 具体场景`，且场景必须**可量化**。

```
会员促销系统效用树
├── 可修改性
│   ├── 折扣规则可修改 → 管理员页面修改后立即生效，无需重新部署
│   └── 策略灵活定义 → 支持用户/商品/地理/时间任意维度自定义
├── 性能
│   ├── 响应时间 → 高峰期商品页响应 < 0.3 秒
│   └── 高并发 → 大促 QPS 峰值 5 万
├── 可用性
│   └── 故障热备份 → 自动检测节点故障并切换备机
└── 可扩展性
    └── 横向存储扩展 → 数据增长可线性扩容存储节点
```

**优先级标注**：`(业务价值, 技术难度)` = `(H/M/L, H/M/L)`

**排序论证模板**：
> "**【场景】应排最高优先级**：① **业务价值 H** —— 直接关系【GMV/用户体验/合规】，【量化影响，如每增加 100ms 转化率降 1%】；② **技术难度 H** —— 涉及【多重技术耦合点】，是架构核心瓶颈。ATAM 要求优先关注**高业务价值且技术风险大**的场景。"

## 问 2（9 分）· 3 个敏感点 + 2 个权衡点

### 敏感点（≥3 个，类型需不同）

| # | 敏感点 | 判定理由 |
|---|---|---|
| 1 | **Kafka 分区数 = 100 + 按设备 ID 哈希分区** | 直接决定告警的**顺序性与吞吐能力**：分区过少则单分区热点导致延迟超标，过多则元数据膨胀 |
| 2 | **边缘节点本地 SQLite 24 小时缓冲** | 直接决定**断网容忍上限**，是可用性 99.95% 目标的关键保障；容量不足则数据丢失 |
| 3 | **5G 专网双活（电信主、移动备）** | 直接决定基地↔云端**链路可用性**，影响故障切换 < 60s 目标 |

### 权衡点（≥2 个，必须双向）

| # | 权衡点 | 双向影响 |
|---|---|---|
| 1 | **国密 SM2 双向 mTLS 认证** | **安全性（+）** 防伪造设备 ↔ **性能（−）** 握手开销与 CRL 同步带来 **10–30ms** 额外延迟 |
| 2 | **Flink 实时流处理告警规则** | **实时性（+）** 规则更新即生效 ↔ **资源消耗（−）** 比批处理多耗 **30%–50% CPU**，且状态管理复杂度高 |

❌ **你的失分**：权衡点只答 1 个（mTLS）；敏感点理由只写"增加可用性"（缺"**直接决定了 XX 目标**"句式）；把"存储层三件套"当敏感点（那是方案堆叠，不是单一关键决策）。

## 问 3（8 分）· 性能战术（≥3 条，含类别）

| 战术 | 类别 | 在本架构的落地 | 量化 |
|---|---|---|---|
| **事件驱动 + 异步** | 减少计算路径 | Kafka 解耦云边、Flink 实时消费，告警从"轮询数据库"改为"流式触发" | 延迟由秒级降至 **50ms 内** |
| **就近计算** | 减少计算 | EdgeX 在边缘节点本地完成协议解析与初步过滤，仅上行有效数据 | 链路传输量降 **80%** |

| **多级缓存** | 缓存 | 边缘 SQLite + 云端 Redis 缓存设备元数据，规则匹配无需查 PG | — |
| **批量与并发** | 并发 | Flink 分区并行消费 Kafka 100 个分区 | 吞吐 ≥ **20 万 TPS** |

⭐ 高分技巧：用"**就近计算 + 减少传输 + 异步解耦**"组合拳，体现"边缘智能"架构高度。

# 第三部分 · 2024 真题满分答案（AI 智能问答平台，25 分）

> 来源：2024 年 11 月系统架构设计师案例分析 试题一（回忆版）

## 问 1（6 分）· 质量属性识别

| 编号 | 需求 | 满分答案 |
|---|---|---|
| (1) | 千万级并发，平均响应 < 2s | **性能（Performance）** |
| (2) | 全年可用率 99.99% | **可用性（Availability）** |
| (3) | 全程加密防泄露 | **安全性（Security）** |
| (4) | 新模块上线不影响现有服务 | **可修改性（Modifiability）** |
| (5) | 兼容 iOS / Android / Web | **兼容性（Compatibility）** |
| (6) | 10 分钟内完成基本操作 | **易用性（Usability）** |

⭐ **两个易混点**：
- (2) **可用性 ≠ 可靠性**：可用性看**在线时间比例**（99.99%），可靠性看 **MTBF/故障率**
- (5) **兼容性 ≠ 可移植性**：兼容性是**多端都能用**，可移植性是**能搬到别的环境**

❌ **你的失分**：(5) 答成"可移植性"（应为兼容性）；(6) 答"易操作性"（标准名为易用性，意思对可给分）。

## 问 2（10 分）· Ping/Echo 与心跳实现原理

### Ping/Echo（主动权在**监控端**）

> **监控组件主动、周期性地**向被监控组件发送 **Ping** 请求；被监控组件收到后**回发 Echo** 响应。若监控组件在超时时间内**未收到 Echo**，即判定该组件发生故障。
> **特点**：请求-响应**双向**通信；监控 N 个节点需发起 N 次往返。

### 心跳 Heartbeat（主动权在**被监控端**）

> **被监控组件主动、周期性地**向监控组件发送一条**简短的心跳消息**；监控组件在预设周期内**未收到心跳**，即判定该组件故障。
> **特点**：**单向**通告；监控端仅被动接收。

⭐ **关键认知**：两者都是**架构战术（软件层面的故障检测模式）**，**不是 ICMP ping 命令**，实现可用任意协议（TCP/HTTP/RPC/自定义）。

❌ **你的失分**：写成"发送 ICMP 协议包""发送 HTTP 包、根据是否有响应"——把架构战术误当网络命令，且把心跳说成请求-响应（与"主动权在被监控端"自相矛盾）。

## 问 3（9 分）· 为什么选心跳（4 维度，答 3 个即满分）

| 维度 | 满分论证 |
|---|---|
| **① 网络开销减半** | 心跳是**单向消息**，流量约为 Ping/Echo 的 **1/2**（后者需请求+响应两个包）。千万级节点下节省的带宽与包处理量极为可观 |
| **② 监控端压力小** | 千万级节点时，Ping/Echo 要求监控端维护**千万个定时器并主动发起千万次往返**；心跳模式下监控端只需**被动接收**并检查"上次心跳时间"，压力下降一个数量级 |
| **③ 故障识别更快** | 心跳**丢失即判定**，无需等待 Echo 超时往返（省掉一个 RTT），故障发现更及时 |
| **④ 可附带状态信息** | 心跳消息可顺带携带 **CPU、QPS、内存**等运行指标，实现"健康检查 + 指标采集"合一，避免额外采集开销 |

⭐ **答题格式**：`【维度名】 + 具体论证`，缺维度名扣分。

❌ **你的失分**：4 条全无维度名，且"安全""更精确"与心跳毫无关系（0.5/9）。

# 第四部分 · 考前速记（进考场前 5 分钟看这个）

## 案例答题五条军规

1. **先数题干有几个决策、几个小问**，答完**逐项清点**再交卷（防漏答）
2. **六元组逐行写**，不写段落；**环境写模式**；**度量带数字**
3. **四类点每条必附"因为……"**
4. **战术必须"【类别】+ 落地 + 量化"三层**
5. **问几就答几**，每问按分值分配时间（25 分 ≈ 25 分钟）

## 高频混淆对（考前扫一眼）

| A | B | 判定钥匙 |
|---|---|---|
| 敏感点 | 权衡点 | 单属性="敏感"；一升一降="权衡" |
| 可用性 | 可靠性 | 在线比例 vs MTBF |
| 兼容性 | 可移植性 | 多端能用 vs 能搬环境 |
| Ping/Echo | 心跳 | 监控端主动 vs 被监控端主动 |
| 3NF | BCNF | 主属性有无豁免 |

## 万能加分句

- "该决策是**敏感点**，因为它**直接决定**了【属性】目标的达成。"
- "【加密】是**权衡点**：**提升安全性**但**增加约 10% CPU 开销**。"
- "识别出该**风险点**后，建议引入【熔断/持久化/多活】战术，将其**转化为非风险点**。"
- "依据 **ATAM 第 5 步（效用树）**，【场景】为最高优先级，应在架构决策中优先保障。"

## 📋 题目回顾

**场景**：某视频直播平台弹幕系统，架构链路：

```
客户端 → 接入网关 → Kafka → Flink（过滤/聚合）→ Redis（广播）→ 各客户端
```

**关键指标**：峰值 **100 万条/秒**弹幕、端到端延迟 **< 200ms**、服务可用性 **99.99%**

## 练 1 · 六元组（3/8）

### 你的答案 vs 满分答案

| 元素 | 你的答案 | 满分答案 | 判定 |
|---|---|---|---|
| ① 刺激源 | 直播间的用户 | 热门直播间的观众客户端（峰值在线 200 万人） | △ 方向对，缺规模 |
| ② 刺激 | 发送弹幕 | 开播瞬间并发发送弹幕消息，峰值 100 万条/秒 | ✗ 太笼统，**缺数量** |
| ③ 制品 | 直播间 | 弹幕处理链路（接入网关、Kafka 集群、Flink 过滤集群、Redis 广播服务） | ✗ **制品 = 被影响的系统部件**，不是业务场所 |
| ④ 环境 | 峰值时期 | 高峰运行模式（热点直播间开播，已按峰值容量弹性扩容） | △ 规范写法是"高峰运行模式" |
| ⑤ 响应 | 保证直播间正常处理峰值弹幕 | 系统接收并过滤弹幕，按直播间聚合后广播给该房间内全部在线客户端 | ✗ **响应 = 系统做了什么动作**，不是目标 |
| ⑥ 响应度量 | 延迟 < 200ms、可用性 99.99% | 端到端延迟 < 200ms，吞吐量 ≥ 100 万条/秒，弹幕零丢弃 | △ 只留本场景相关度量 |

### ✅ 满分答案（可直接背的形态）

```
① 刺激源：热门直播间的观众客户端（峰值在线 200 万人）
② 刺激　：开播瞬间并发发送弹幕消息，峰值 100 万条/秒
③ 制品　：弹幕处理链路（接入网关、Kafka 集群、Flink 过滤集群、Redis 广播服务）
④ 环境　：高峰运行模式（热点直播间开播，系统已按峰值容量弹性扩容）
⑤ 响应　：系统接收并过滤弹幕，按直播间聚合后广播给该房间内全部在线客户端
⑥ 响应度量：端到端延迟 < 200ms，吞吐量 ≥ 100 万条/秒，弹幕零丢弃
```

### 🪝 三句铁律

1. **"刺激源是'谁'，制品是'系统哪部分挨打'，响应是'系统做了什么动作'。"**
2. **"刺激必须有量（多少并发 / 多少条），度量必须有数字。"**
3. **"度量只写本场景相关的指标——不要把平台整体目标混进来。"**（可用性 99.99% 属于全局目标，不属于本性能场景）

## 练 2 · 战术（5/9）

### ✅ 满分答案

```
① 【引入并发 / 资源池】：提升 Flink 集群并行度，并按直播间 ID 分区，使 100 万条/秒
   弹幕在多个并行子任务中同时处理，避免单分区积压导致端到端延迟上升。

② 【异步（事件驱动）】：弹幕全链路异步传递（网关 → Kafka → Flink → Redis），
   生产者与消费者彻底解耦，消除同步等待造成的延迟叠加。

③ 【就近访问 / 缓存】：Redis 广播层缓存直播间在线连接与热度数据，
   弹幕直接由内存广播下发，避免回查数据库，压缩处理链路耗时。
```

## 练 3 · 多维论证（0.5/8）

### ✅ 满分答案

```
① 【吞吐能力】：Kafka 单分区可支撑数十万条/秒写入，通过增加分区可水平扩展至
   百万级；而同步 RPC 每次调用独占线程与连接，支撑 100 万 QPS 需要海量线程池与
   连接资源，接入网关会先成为瓶颈。

② 【削峰与故障解耦】：弹幕流量突发性极强（开播瞬间暴涨）。Kafka 作为缓冲层先
   承接洪峰，Flink 按自身处理能力平滑消费；若下游 Flink 或 Redis 短时故障，
   消息仍持久化在 Kafka 中不丢失。同步 RPC 下，下游一旦抖动或宕机会直接阻塞
   上游网关，引发级联雪崩。

③ 【可扩展性】：新增弹幕审核、统计等消费方时只需订阅同一 topic，无需改动生产者；
   同步 RPC 则需逐一改造整条调用链。
```

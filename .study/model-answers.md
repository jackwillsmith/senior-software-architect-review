## 一、弹幕系统三练（案例论述标准答案）

**场景**：视频直播平台弹幕系统
**架构链路**：客户端 → 接入网关 → Kafka → Flink（过滤/聚合）→ Redis（广播）→ 各客户端
**关键指标**：峰值 100 万条/秒弹幕、端到端延迟 < 200ms、服务可用性 99.99%

---

### 练 1 · 性能质量属性场景六元组（8 分）

```
① 刺激源：热门直播间的观众客户端（峰值在线 200 万人）
② 刺激　：开播瞬间并发发送弹幕消息，峰值 100 万条/秒
③ 制品　：弹幕处理链路（接入网关、Kafka 集群、Flink 过滤集群、Redis 广播服务）
④ 环境　：高峰运行模式（热点直播间开播，系统已按峰值容量弹性扩容）
⑤ 响应　：系统接收并过滤弹幕，按直播间聚合后广播给该房间内全部在线客户端
⑥ 响应度量：端到端延迟 < 200ms，吞吐量 ≥ 100 万条/秒，弹幕零丢弃
```

---

### 练 2 · 性能战术（9 分）

```
① 【引入并发 / 资源池】：提升 Flink 集群并行度，并按直播间 ID 分区，使 100 万条/秒
   弹幕在多个并行子任务中同时处理，避免单分区积压导致端到端延迟上升。

② 【异步（事件驱动）】：弹幕全链路异步传递（网关 → Kafka → Flink → Redis），
   生产者与消费者彻底解耦，消除同步等待造成的延迟叠加。

③ 【就近访问 / 缓存】：Redis 广播层缓存直播间在线连接与热度数据，
   弹幕直接由内存广播下发，避免回查数据库，压缩处理链路耗时。
```

---

### 练 3 · 多维论证：异步消息 vs 同步 RPC（8 分）

```
① 【吞吐能力】：Kafka 单分区可支撑数十万条/秒写入，通过增加分区可水平扩展至
   百万级；而同步 RPC 每次调用独占线程与连接，支撑 100 万 QPS 需要海量线程池与
   连接资源，接入网关会先成为瓶颈。

② 【削峰与故障解耦】：弹幕流量突发性极强（开播瞬间暴涨）。Kafka 作为缓冲层先
   承接洪峰，Flink 按自身处理能力平滑消费；若下游 Flink 或 Redis 短时故障，
   消息仍持久化在 Kafka 中不丢失。同步 RPC 下，下游一旦抖动或宕机会直接阻塞
   上游网关，引发级联雪崩。

③ 【可扩展性】：新增弹幕审核、统计等消费方时只需订阅同一 topic，无需改动生产者；
   同步 RPC 则需逐一改造整条调用链。
```

## 二、ATAM 四类点 · 满分判定与话术

### 敏感点
> "KubeEdge 采用 1 主 2 从部署是**敏感点**，因为它**直接决定**了边缘节点在单点故障时的**可用性**目标（年可用性 99.95%、故障切换 < 60 秒）能否达成。"

### 权衡点
> "全链路 HTTPS + AES-256 加密是**权衡点**，它**同时影响安全性（+，防中间人攻击、满足等保要求）**和**性能（−，TLS 握手与加解密带来约 10% 的 CPU 开销）**。"

### 风险点（附缓解战术，可加分）
> "促销服务作为单体保留且未接入熔断限流是**风险点**，存在被异常流量击穿后波及订单服务的**隐患**，**可能**威胁可用性目标。**建议引入 Sentinel 熔断 + 只读副本拆分，将其转化为非风险点。**"

### 非风险点
> "Kubernetes 跨 3 可用区部署 + Istio 流量治理是**非风险点**，二者均为 **CNCF 毕业项目**、生产级成熟方案，**无技术不确定性**。"

### 不纳入 ATAM
> "办公椅更换与系统架构**无关**，**不纳入 ATAM 评估范围**。"

## 三、Ping/Echo vs 心跳（真题问 3 满分论证）

**结论**：本系统（千万级用户并发）选择**心跳模式**更合适。

```
① 【网络开销】维度：心跳为被监控端发出的单向消息，流量约为 Ping/Echo 的一半
   （后者需要请求 + 响应两个包）。千万级节点规模下，节省的带宽与包处理量极为可观。

② 【监控端压力】维度：千万级节点时，若采用 Ping/Echo，监控端需维护千万个定时器
   并主动发起千万次往返请求；心跳模式下监控端仅需被动接收并检查"上次心跳时间"，
   压力下降一个数量级。

③ 【故障识别速度】维度：心跳丢失即可判定故障，无需等待 Echo 超时往返（省去一个
   RTT），故障发现更及时，有助于满足 99.99% 可用性目标下的快速切换要求。

④ 【附带状态信息】维度：心跳消息可顺带携带 CPU、QPS、内存等运行指标，实现
   "健康检查 + 指标采集"合一，避免额外采集开销。
```

## 四、规范化判定（候选键与范式）

**R(A, B, C, D)，F = {A→B, B→C, A→D}**

```
① 属性分类：L = {A}；R = {C, D}；LR = {B}；N = ∅
② 求闭包：A⁺ = {A} →(A→B)→ {A,B} →(B→C)→ {A,B,C} →(A→D)→ {A,B,C,D} = U ✓
③ 候选键 = A（唯一）；主属性 = {A}；非主属性 = {B, C, D}
④ 2NF 检查：候选键为单属性 → 不可能存在部分依赖 → 满足 2NF ✓
⑤ 3NF 检查：A→B 且 B→C（B ↛ A）→ 存在传递依赖 → 违反 3NF ✗
⑥ 结论：最高满足 2NF
```
